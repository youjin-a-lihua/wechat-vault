# 微信数据方舟 · 计划书

> 版本 v3.0 · 2026-10-01 · **单容器一体化方案**  
> 定位：开源、可 Docker 部署的微信聊天记录归档系统  
> 目标：对标并超越微备份（WxBackup），一个容器、一个端口、一条命令

---

## 一、项目初衷（不可动摇）

1. **破除垄断** —— 微备份闭源、付费、把聊天记录交给第三方。我们要一个开源自部署的等价物。
2. **走官方通道** —— 用微信自己的「聊天记录迁移与备份」拿数据，**不破解、零法律风险**。
3. **不占日常登录位、空闲 0 常驻** —— 归档完即停，不长期挂机。

### 已排除的弯路（记录在案）

| 弯路                    | 为什么错                                   |
| --------------------- | -------------------------------------- |
| ❌ 官方导出 CSV 拿附件        | 导出包不含附件原图                              |
| ❌ iOS 加密备份 + 扫内存取密钥   | 备份加密、且不含目标数据                           |
| ❌ 自写解密器对抗 `.dat` 加密   | ~~根本不需要对抗~~ **2026-10-02 更正：Linux 迁移落盘确实是加密的，必须解码** |
| ❌ 拆成两个容器（方舟 + WOC 面板） | 引入 docker.sock 高危面，拼装感，违背"对标一个 exe"的初衷 |

---

## 二、微备份的真实原理（已核实）

```
微备份（内嵌微信客户端的桌面程序）
  ① 弹二维码 → 扫码登录一个真实微信会话
  ② 点「备份」→ 手机微信弹出相同备份界面
  ③ 手机经 WiFi 走官方「聊天记录迁移与备份」把整包数据传过来
  ④ 落盘 → 解析 → 导出可读格式
```

**微备份的价值不在"会解密"，而在"它内置了一整个微信运行时"。**  
数据由微信自己交出，全过程没有任何破解。**它就是一个 exe，所以我们也应该是一个容器。**

## 三、架构：单容器一体化

```
┌──────────────────────────────────────────────────────────────┐
│  用户浏览器  →  http://<NAS>:8790                            │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │  微信数据方舟（一个容器）                                 │  │
│  │                                                        │  │
│  │   ① 微信运行时（复用 WOC 技术）                          │  │
│  │      Xvfb 虚拟显示 + 官方微信 Linux 版 + KasmVNC 串流    │  │
│  │      → 扫码登录、接手机 WiFi 迁移                        │  │
│  │                    ↓ 数据落盘                            │  │
│  │   ② 归档器（我们的）                                     │  │
│  │      扫描 → 指纹 → 幂等入库                              │  │
│  │                    ↓                                    │  │
│  │   ③ 存储 + 检索（我们的）                                │  │
│  │      SQLite FTS5 + trigram 中文分词                      │  │
│  │                    ↓                                    │  │
│  │   ④ Web 界面（我们的）                                   │  │
│  │      会话列表 / 消息流 / 搜索 / 导出                      │  │
│  └────────────────────────────────────────────────────────┘  │
│                                                              │
│  数据卷：/data  （微信数据 + 归档库 + 全文索引）               │
└──────────────────────────────────────────────────────────────┘
```

### 关键设计

| 设计点       | 说明                                  |
| --------- | ----------------------------------- |
| **一个容器**  | 微信运行时 + 方舟本体同容器，**不需要 docker.sock** |
| **一个端口**  | 8790 一个入口，微信桌面通过内嵌页面访问              |
| **一个数据卷** | `/data` 存放微信数据与归档库，备份它 = 备份全部       |
| **不魔改微信** | 用腾讯官方 Linux 版 deb                   |
| **只读局域网** | 端口只绑内网 IP，绝不 `0.0.0.0`              |

### 与两容器方案的对比

|             | 两容器                | **单容器（本方案）**                  |
| ----------- | ------------------ | ----------------------------- |
| 部署          | 两套 compose + 跨容器挂卷 | **一条 `docker compose up -d`** |
| 端口          | 36080 + 8790       | **一个 8790**                   |
| docker.sock | 必须挂（高危）            | **不需要（消灭高危面）**                |
| 用户操作        | 两个界面来回切            | **一个界面**                      |
| 对标微备份       | 拼装感                | **就是一个完整体**                   |

## 四、数据流（端到端）

```
① 手机微信 → 我 → 设置 → 聊天记录迁移与备份 → 迁移到电脑
② 方舟里运行的微信收到数据，落到 /data 下的明文库
③ 归档器扫描该目录 → 识别聊天记录 → 计算指纹 → 幂等入库
④ 附件（图/视频/文件）随数据一并落盘，**直接可读**
⑤ Web 界面：全文搜索、按会话浏览、时间轴查看、导出
```

> ⚠️ **2026-10-02 实测更正（此前判断有误）**：上面这条只在
> **Windows 版「导出聊天记录」** 时成立。手机把聊天记录**迁移**到
> **Linux 版微信**（即本方案容器内那一个）时，落盘的是
> **SQLCipher 加密库 + V2 加密的 `.dat` 附件**——**必须解码才能读**。
>
> 因此「附件不需要解码」这句在容器方案下**不成立**，已作废。实际链路是：
> ① 离线派生账号级密钥解 V2 内层 → ② 图片/语音/视频/文件/表情分别解码/关联
> → ③ 其中约 13% 的「原图」是 `wxgf`（内层为标准 HEVC），用容器内 ffmpeg 还原。
> 详见 `原图WxAM攻坚计划.md` 与 `验收报告_2026-10-02.md`。

## 六、红线（不可违反）

1. **绝不开公网** —— 端口只绑内网 IP，禁止 `0.0.0.0`。
2. **走官方通道** —— 用微信「迁移与备份」拿数据，不冒充客户端、不实现微信私有协议。
   ⚠️ **2026-10-02 定位调整（用户裁决 = B）**：本机归档链路包含**离线解密**
   （V2 密钥离线派生 + WxAM 解码）。原始「零解密」表述已不适用，理由见 §3.x 更正说明。
3. **不占日常登录位** —— 归档完成可按需停止，空闲 0 常驻。
4. **不修改微信客户端** —— 用腾讯官方原版。
5. **不引入 docker.sock** —— 单容器，消灭高危面。
6. **百分百可交付才交付** —— 每阶段实测通过再进下一阶段。

## 七、风险与对策

| 风险                        | 影响        | 对策                                |
| ------------------------- | --------- | --------------------------------- |
| 单容器内跑 GUI + 服务，进程管理复杂     | 微信崩了要能自愈  | 用 WOC 的 `autostart` 方案（微信崩溃自重启）   |
| 登录会话定期失效                  | 需重新扫码     | 内嵌微信桌面，随时可重扫                      |
| NAS 拉不到镜像 / 微信 CDN        | 装不起来      | 切国内源；微信 deb 支持主备 CDN 回退           |
| 微信风控（设备伪装）                | 账号可能被强制退出 | 复用 WOC 的 machine-id/hostname 伪装方案 |
| 容器内存占用                    | NAS 内存紧张  | 单实例空闲 ~0.6GB；归档完即停                |
| Linux 版微信库结构与 Windows 版不同 | 解析器需适配    | **阶段二先实测落盘结构**，再写解析               |
| 镜像体积（含 KasmVNC + 依赖）      | 拉取慢       | 微信本体不打进镜像，运行时下载                   |
