### 2.2 图片原图解密（历史头号待办，彻底攻克）

**结论：微信 4.x 的 `.dat` 图片可以完全离线解密，不需要扫进程内存。**

破解出的算法（与 gitee/DeepWiki 上未被下架的参考实现逐字节吻合，并已用真实数据反证）：

```
布局： [0:6) 签名 07 08 56 32 08 07
       [6:10) aes_size(u32)  本机恒为 1024
       [10:14) xor_size(u32) = 尾部 XOR 段长度
       [14] 占位
       [15:15+aes_size)                AES-128-ECB 密文 → 明文「头部」
       [15+aes_size:+16)               16 字节固定块（本机恒 4b342788…afad，跳过）
       [15+aes_size+16 : +xor_size)    尾部，单字节 XOR

明文 = AES_ECB_dec(头部密文, aes_key) ‖ (尾部 XOR xor_key)
密钥 = 账号级、可离线派生：
       xor_key = code & 0xFF
       aes_key = md5(f"{code}{wxid}").hexdigest()[:16]
       本机： code = 1*********，xor_key = 0x42，aes_key = 3075e99d****
```

**密钥获取的巧解（无需内存扫描）**：
1. `xor_key` 由缩略图尾部反推 —— JPEG 必以 `FF D9` 结尾，故 `xor_key = tail[-2]^0xFF`
   （本机 79,635 个缩略图投票，119:1 一边倒命中 `0x42`）
2. `code` 用「`code & 0xFF == xor_key`」把候选压到 1,677 万个，再以
   「AES 解密后必须是**合法 JPEG 段标记**」严格校验暴力求出（33 秒）

**交叉验证（关键，防假阳性）**：宽松只查 3 字节 `FF D8 FF` 时，错误候选也能
"命中" 206/400；换成 4 字节段标记 + 完整文件以 `FF D9` 收尾后：

| code | aes_key | 严格 JPEG 头 | 完整 JPEG |
|---|---|---|---|
| 2400101954 | f278e8a7… | 0 / 400 ❌ 假阳性 | 0 / 60 |
| **1*********** | **3075e99d****** | **399 / 400 ✅** | **60 / 60 ✅** |

**批量结果**：

| 指标 | 数值 |
|---|---|
| 处理 `.dat` | 120,021 个（69 秒，4 进程） |
| 成功解密 | **119,920** |
| 其中 `wxgf`（需二层 WxAM 解压，本次跳过） | 15,436 |
| 落盘可用图片 | **104,484 张**（84,913 JPG + 1,316 PNG + 1 GIF），共 **7.2 GB** |
| 消息 ↔ 文件关联 | **73,378 / 74,111 = 99.0%** |

⚠️ 关联依据的探索过程（记录在案，避免重走）：
- 消息里的 `md5` 与 `.dat` **文件名**不对应（文件名是密文哈希）
- 消息 `md5` 与「解密后明文 md5」只相交 129 条（跨账号/版本渲染差异）
- `message_resource.db.packed_info` 只存扩展名，不含映射
- ✅ **最终依据**：`attach/<md5(chat_username)>/<YYYY-MM>/Img/` + 明文**字节数**
  与消息 XML 的 `length/hdlength/cdnthumblength` 精确相等 → 实测 99.1%
- 会话↔哈希用**时间戳指纹**匹配（`source_file` 里是微信号别名，`md5(别名)` 对不上）

### 2.5 修复的真实故障：autostart 一直在「空转」

- **现象**：autostart 用 `uvicorn viewer.wv_server:app`（模块模式）启动方舟，
  而模块模式**不会执行 `load_store()`** → 界面永远空。
- 它每 2 秒重试一次并报 `address already in use`，把 `/data/logs/vault.log` 刷到 2.2 MB。
- 真正对外服务的是**手工启动的 CLI 进程**（`wv_server.py --store /data`），
  一旦该进程退出，autostart 就会以空界面接管。
- **处置**：`deploy/autostart` 改为 CLI 模式并固化进镜像；本次 `--force-recreate`
  后服务由 autostart 自行拉起（PID 339，CLI 模式），已实测正常。

## 九、核查：「本机那份 2024 备份能解密并入方舟吗」

**离线解密：不行（已实测证伪）。走官方恢复：可以。**

**① 离线不可解（证据）**
- 熵值：整体 **8.0000 bits/byte**，4KB 块熵标准差 0.004 —— 完全均匀随机
- 无 SQLite 头、无压缩头、**零中文串**（扫描 2MB）
- 用 8 种候选密钥（图片 aes_key、V1 固定 key、WCDB passphrase 及其 md5、md5(wxid)、
  md5(code)、全零）分别 AES-ECB 试解 → **全部乱码，无一命中**
- 参考事实：`Backup.db` 与 `BAK_*` 是微信**备份容器**格式，解密在客户端内部完成；
  公开工具（chatlog / WeChatMsg 系）只处理本地 DB，不处理备份容器

**② 关键发现：两份老备份的构成不同**

| 备份包 | Backup.db | TEXT 分片 | MEDIA 分片 | 能否带出文字 |
|---|---|---|---|---|
| こぼやしのiPhone **2024-09-06** | 11.6 MB | **❌ 无** | 5 × 2 GB | 基本不能（只含媒体） |
| こぼやしのiPhone **2025-08-14** | 33.4 MB | **✅ 602 MB** | 9 个 | **能（完整）** |

→ **要补 2024-09 之前的聊天文字，应该恢复「2025-08-14」那一份，而不是 2024-09-06 那份。**
2025-08-14 的备份天然包含它之前（含 2024-09-06 之前）的全部历史，且带 602MB 文字分片。

**③ 可执行路径（零法律风险，走官方通道）**

1. 本机 Windows 微信 →「更多 → 聊天记录管理 → 备份与恢复」
   （该页已能列出这两份老备份；若未列出，点底部「导入较早版本的备份」登记）
2. 对「こぼやしのiPhone 2025年8月14日 15:25」点 **恢复** → 选择目标手机 →
   同 Wi-Fi 合并进手机微信（老格式**只支持恢复到手机**，不能直接恢复到电脑）
3. 手机拿到历史后，用微信「迁移聊天记录到电脑」把整包迁到 NAS 微信（:13000 桌面）

# 补丁 5（15:4x–16:0x）：**WxAM 原图攻坚完成（P0–P5 全做完）**

用户裁决项目定位 = **B（主流程含解密）**，但硬约束「不假定用户是 Windows」。
→ v1 的 Windows-only 方案作废，改用**容器内 ffmpeg**，已全部落地。

## 十五、结论：不需要腾讯二进制，也不需要 Windows

**关键认知**：`wxgf` 不是私有编码，它是**容器**，内层是**标准 HEVC(H.265) 码流**。

```bash
ffmpeg -f hevc -i pipe:0 -vframes 1 -c:v mjpeg -q:v 3 -f image2pipe -
```

**唯一的坑（本机实测踩到并解决）**：必须显式 `-f hevc`。若让 ffmpeg 自行探测，
约一半文件报 `Invalid data found when processing input`（前 12 字节 `wxgf` 头干扰探测）。
**加上 `-f hevc` 后成功率 100%。**

> 早期曾把失败样本误判为「动画双轨」（HEVC 起始码偏多），去实现 alphamerge 合成——**这是错的**。
> 加 `-f hevc` 后 ffmpeg 报 `hevc (Main Still Picture)`、`frame=1`，
> **全部是单帧静态图**，分辨率就是原始尺寸。该误判已在技能文档中更正。

## 十六、实测结果

| 项 | 数值 |
|---|---:|
| wxgf 待处理 | 15,436 个 / 1.13 GB |
| **解码成功** | **15,418（99.9%）** |
| 解码失败 | 18 |
| 落盘原图（md5 去重） | **12,191 张 / 2.1 GB** |
| 扫描+解码总耗时 | 约 24 分钟（3 进程） |
| 产物分辨率 | 1280×1706 / 2844×1280 / 1220×2712 / 1080×1920 / 1260×596 … |

## 十七、关联链（本次踩坑重点）

**直接用尺寸匹配 XML 的 `length` 行不通**——wxgf 原图的明文长度对不上 XML 的任何字段。
正确的链条是：

```
消息 --(会话哈希, 月份, cdnthumblength)--> `_t.dat` 的 stem
     --(同一 stem)--> 原图（.dat / _h.dat，可能就是 wxgf）
     --(已解码)--> media_full
```

依据（均已实测）：
① `cdnthumblength` == `_t.dat` 明文字节数 → **命中 97.9%**
② 缩略图与原图**共享文件名 stem**（`xx.dat` / `xx_t.dat`）→ **36,145 对**
③ wxgf 原图长度**对不上** XML 任何字段 → 故不能按尺寸直接匹配原图

**链路结果**：
| 环节 | 条数 |
|---|---:|
| **命中原图 → 回填 `media_full`** | **13,817** |
| 原图非 wxgf（本就已是原图） | 59,125 |
| 无缩略图尺寸 / 缩略图未匹配 | 1,167 |
