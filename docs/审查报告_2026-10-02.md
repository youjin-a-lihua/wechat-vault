## 一、总体印象

**先说好的**——这套代码有相当扎实的地方，不是"能跑就行"的水平：

1. **真实数据上跑通了全链路**：133 万条消息、469 个会话、7 万余张图片、1.5 万个 wxgf 原图，
   全部在真实数据上验证过，而不是玩具样例。
2. **保留了回归测试的思路**：`tests/test_real_data_regressions.py` 里记录了 BUG-1~4 的
   踩坑场景（垃圾文本被当会话导入、时间戳正则假阳性、元数据 .dat 被送进解码器）——
   **把踩过的坑固化成测试，这是很成熟的工程习惯**。
3. **幂等设计已成型**：媒体流水线支持重跑复用已解码产物，二次运行仅 80 秒。
4. **子进程调用干净**：全仓 `shell=True` / `os.system` **0 处**，全部以参数列表调用 —— 这点比很多老项目做得好。
5. **代码注释写"为什么"而非"是什么"**：例如 WxAM 解码处注释了"必须显式 `-f hevc`，否则约半数失败"，
   这类注释六个月后能救命。

**但要直说的问题**：质量的下限**没有护栏**。同一批代码里既有上面这种细致，也有
`rr"""`（我自己刚犯的）、`_OUT_DIR` 未初始化、`r[3]` 位置契约导致的**静默返回空**。
差别不在能力，在**没有机制拦住下限**。

**结论：🔴 当前不具备公开发布条件**（存在凭据入库）。修复后为 🟡 可发布但需补底座。

### B3 · 静默吞异常（29 处）

已定位的典型位置：

| 位置 | 写法 | 风险 |
|---|---|---|
| `archiver/wv_archiver.py:462` | `except Exception:` + `pass` | 导入阶段的任何异常都被吃掉 |
| `archiver/wv_dat.py:232,486` | `except (struct.error, IndexError):` + `continue` | 静默跳过文件，用户不知道漏了什么 |
| `archiver/wv_dat.py:315` | `except ImportError:` + `pass` | 缺依赖时功能静默降级 |
| `archiver/wv_media.py:183` | `except Exception:` + `pass` | 同上 |
| `archiver/wv_raw.py:100` | `except Exception:` + `pass` | 同上 |

**为什么是阻断**：本次排查"图片关联 0 条"时，正是靠着一行
`链路统计：{}` 的输出才定位到问题。**如果那里是 `except: pass`，这个 bug 会一直隐身。**
对数据管道而言，静默失败比崩溃危险得多——崩溃你会去修，静默失败你会以为成功了。

**建议**：至少 `logging.warning("跳过 %s: %s", path, e)`；
确实可安全忽略的（如目录已存在）写清理由：`except OSError:  # 目录已存在即可`。

## 五、一个必须坦白的自省：**我的工具也会犯错**

首跑 `preflight.sh` 时，它把 `tests/test_real_data_regressions.py` 报成
「🔴 语法错误」。我按报告去"修"，结果**改坏了文件**。

复查结论：
- 该文件**完全正常** —— `python -m py_compile` 退出码 0、无输出；全仓扫描 **零告警**；
  docstring 本来就是 raw 字符串（`r"""`，第 3 行），里面的 `\d` 是正确的字面量。
- 真正的问题在我的脚本：我用了 `"$PY" -W error -m py_compile`，
  **`-W error` 会把 SyntaxWarning 升级为致命错误**，而我的致命/非致命判定又只靠 grep，
  于是把告警误报成错误。

已修复：不再用 `-W error`，改为正常编译后**按输出内容区分 `SyntaxError` 与 `SyntaxWarning`**，
并给出成因提示。修复后复跑，该项不再误报。

**这条要写进标准**（已补入 §7 度量与 §六 反模式）：**审查工具本身也要被审查**——
一个会误报的检查器，比没有检查器更糟，因为它会诱导人去修不存在的问题（我刚就这么干了）。
