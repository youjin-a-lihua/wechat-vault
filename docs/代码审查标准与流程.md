## 一、分级标准（三档，必须一致使用）

审查意见一律用这三个标记开头，**顺序即优先级**。

### 🔴 阻断（Must Fix，不修不能合并）
不满足就等同于「交付事故」。本项目已确认的阻断类型：

| # | 类型 | 判据 | 本仓库实例 |
|---|---|---|---|
| B1 | **凭据/密钥入库** | 任何口令、token、私钥、pbkdf2 散列、真实内网地址出现在被跟踪文件中 | `tests/_nas_pwhash.txt`；`Zheng2****` 出现在 10 个文件；`192.0.2.10` 出现在 compose/ps1/py |
| B2 | **用户数据/密钥目录未忽略** | `local_keys/`、`store/`、`vault.db`、`media/` 可被提交 | 无 `.gitignore`（已建立） |
| B3 | **静默失败** | `except:` / `except Exception: pass` 吞掉异常且不留痕 | 29 处；`wv_raw.py:100`、`wv_media.py:183`、`wv_archiver.py:462` |
| B4 | **语法/导入期错误** | `py_compile` 不通过、导入即崩 | 检查通过（自动化守住） |
| B5 | **不可复现的依赖** | 无 `requirements.txt`（含 `==` 锁定） | 现状缺失 |
| B6 | **破坏性数据操作无确认/无备份** | 删除、覆盖、迁移类操作前无备份点 | 需专项确认（见 §4.3） |
| B7 | **命令注入面** | `shell=True`、`os.system`、未转义插值进命令 | 当前 0 处 ✅ 保持 |
| B8 | **路径/契约脆弱** | 依赖「参数位置」而非命名契约；同一函数被不同调用方以不同列序调用 | 真实事故：`_conv_hash_map` 固定读 `r[3]`，而 `run_link` 传 3 列、`run_videos` 传 4 列 → 关联结果静默变 0 |

### 🟡 建议（Should Fix，可在 PR 中记录后分批处理）
| # | 类型 | 判据 |
|---|---|---|
| S1 | 宽泛捕获 | `except Exception` 数量增长，或本应收敛到 `sqlite3.Error`/`OSError` |
| S2 | 无结构化日志 | 关键路径只有 `print`，无 `logging` + 级别 |
| S3 | 超长函数 | 单函数 > 80 行（当前 8 个，最长 138 行） |
| S4 | 重复逻辑/重复全扫 | 同一昂贵操作在一次流程里被算两遍（真实案例：`run_wxam` 里 `_plain_sizes` 绕过缓存被扫两次） |
| S5 | 死代码 | 定义后无调用（当前：`archiver/wv_media.py:372 resolve_conv_hash`） |
| S6 | SQL 字符串拼接 | 当前来源是内部常量尚安全，但**是注入的温床**（`wv_archiver.py:335,341`、`wv_server.py:479,497`） |
| S7 | 缺关键路径测试 | 解密、关联、坐标转换这类"错了不报错"的逻辑必须有用例 |
| S8 | 硬编码绝对路径 | 8 处 `/data`、`/vol2`、`/config`，应走环境变量 |
| S9 | 前端内联事件处理器 | 与 CSP 冲突；`viewer/static/app.js` |

### 💭 细节（Nit，不影响合并）
命名、注释与代码不一致、文档缺口、可读性、可选的更优写法。
**规则：一次 PR 里 nit 不超过 5 条**，否则真正的问题会被淹没。

## 二、本项目专属的"红线"（比通用规范更重要）

这四条是**从真实事故里提炼**的，比任何风格规范都值钱：

### 红线 1 · 凭据永不入库
- 一律读环境变量（如 `WV_NAS_HOST`、`WV_SUDO_PASS`），仓库只提供 `env.example`
- **已提交过的凭据 = 已泄漏**。删文件不算撤回，必须**轮换口令**
- 一旦确定要公开仓库：先跑 `bash tools/preflight.sh`，🔴 必须为 0

### 红线 2 · 不许静默失败
> 教训：排查「图片关联 0 条」时，代码打了 `链路统计：{}` 才暴露问题。
> 如果当时写的是 `except: pass`，这个 bug 会一直隐身到用户投诉。

- 禁止 `except: pass`
- 允许忽略时，必须写**为什么可以忽略**：`except OSError:  # 目录已存在即可`
- 关键路径（解密、关联、写库）的每个分支要么成功要么**留下可观测痕迹**

### 红线 3 · 契约用名字，不用位置
> 教训：`_conv_hash_map(conn, rows, ...)` 内部固定读 `r[3]`，而不同调用方传的 SELECT
> 列序不同（3 列 / 4 列）→ 结果是**静默返回空**，看起来"跑成功了"却什么都没做。

- 跨函数传结构体，不传裸 tuple；Python 里用 `dict`/`NamedTuple`/`dataclass`
- 必须传 tuple 时，在函数 docstring 里写明**列序契约**，且**所有调用方保持同序**
- 新增调用方时，先看被调函数的契约，而不是"照着旁边那行抄"

### 红线 4 · 破坏性操作先备份，再动手
- 覆盖/删除用户数据（`vault.db`、媒体目录、密钥）前，先生成可回滚的快照
- 幂等要求：重复执行同一命令，结果必须一致（本项目的媒体流水线已做到——保持）

## 三、审查维度（八问）

审一份 PR，按这八问过一遍，**顺序即重要性**：

1. **正确性** —— 它做的和它宣称的一致吗？边界（空、超大、时区、重复）处理了吗？
2. **安全性** —— 有凭据吗？有注入面吗？鉴权检查在吗？会不会泄漏用户数据？
3. **数据完整性** —— 会写坏库吗？会丢数据吗？失败可回滚吗？幂等吗？
4. **可观测性** —— 出错时能定位吗？关键分支有日志/返回值吗？
5. **可维护性** —— 六个月后别人（或你自己）看得懂吗？函数是否过长？
6. **性能** —— 有 N+1 吗？有重复全扫吗？有阻塞主线程的重活吗？
7. **测试** —— 关键路径有用例吗？这次改动补了吗？
8. **一致性** —— 和既有约定一致吗（命名、错误处理、目录结构）？

## 四、流程：四道闸门

```
 ① 提交人自检      ② 机器体检        ③ 人工审查          ④ 合并门禁
 ───────────      ───────────       ───────────        ───────────
 checklist 过一遍   preflight.sh      按 §3 八问 + §5     PR 模板填完
 补测试/补日志       🔴=0 才能继续      分级意见 + 结论      🔴 全清 + 批准人签字
```

### 4.1 分级授权（按风险决定审查强度）

| 变更风险 | 判定 | 审查要求 |
|---|---|---|
| **低** | 文档、注释、样式微调、纯重命名 | 1 人看过即可（可用异步 review） |
| **中** | 新增接口、前端交互、查询逻辑 | **1 名**审查者 + 机器体检通过 |
| **高** | 密钥/解密逻辑、数据库 schema、归档写入、部署与容器、任何删除/迁移操作 | **2 名**审查者（其中 1 人必须熟悉该模块）+ 必须附**回滚方案** |

> 现实建议：这个项目目前基本是「单人 + AI」在推进，**"2 名审查者"落地不了**。
> 折中做法（**强制**）——高风险变更必须满足以下**三条**才能合并：
> 1. 机器体检 🔴 = 0
> 2. 用**真实数据的只读副本**跑过一次，并留下输出（截图/日志/统计）
> 3. 写明回滚步骤（恢复哪个文件、哪条命令）
>
> 这三条正是本次 WxAM 攻坚时实际采用的模式（先抽样验证 → 再全量 → 备份 `vault.db`）。

### 4.2 审查者的纪律（来自专家守则）

- **一次到位**：一轮里把问题说完，不要"挤牙膏"式多轮补充
- **说为什么**：不只说"改这里"，要说"因为会导致 X"
- **建议而非命令**：用「建议…因为…」，不用「必须改成…」
- **明确标级**：🔴/🟡/💭 一个都不能少
- **表扬好代码**：看到干净的抽象、想周全的边界处理，说出来——这是教人最快的方式
- **不确定就问**：意图不明时先问，别默认对方错了

### 4.3 高风险专项：数据操作三件事

涉及归档写入/迁移/删除时，审查清单里必须逐个回答：

1. **备份点在哪？** （`vault.db` 的副本路径 / 媒体目录不受影响吗）
2. **失败了会怎样？** （半成品状态能否识别？重跑幂等吗？）
3. **怎么回滚？** （具体到命令，不是"重新跑一遍"）

## 五、分领域检查清单

### 5.1 Python / 后端
- [ ] 无 `except: pass`；宽泛捕获有注释说明
- [ ] 无硬编码凭据；地址/路径走环境变量
- [ ] 跨函数传递用命名结构，不用裸 tuple（§红线 3）
- [ ] SQL 值用占位符；表名/列名走白名单
- [ ] 子进程用参数列表，不用 `shell=True`
- [ ] 关键路径有日志（`logging`，带级别）
- [ ] 幂等：重复执行结果一致
- [ ] 单函数 ≤ 80 行，超出则拆分并说明理由

### 5.2 数据管道 / 解密 / 关联（本项目特有，最高风险）
- [ ] **每个关联判据都在真实数据上量过命中率**，并把数字写进代码注释或文档
- [ ] 无法命中时**降级路径明确**（如：拿不到原图 → 用缩略图，而不是空白）
- [ ] 抽样验证脚本保留在 `tests/`，可重跑
- [ ] 全量执行前先在样本上验证（本次流程：抽样 8 个 → 60 个 → 全量）
- [ ] 输出目录结构与既有约定一致，且幂等（已存在则复用，不重复计算）
- [ ] 新依赖（如 `ffmpeg`、`pilk`）**写进 Dockerfile**，不留在容器可写层

### 5.3 前端
- [ ] 不用内联事件处理器（`onclick=`/`onerror=`）
- [ ] 用户数据一律 `esc()` 转义后再进 DOM（XSS）
- [ ] 交互反馈挂在按下（`:active`），不只在完成后
- [ ] 尊重 `prefers-reduced-motion`
- [ ] 大列表不阻塞：图片 `loading="lazy"`、按需加载原图
- [ ] 改动 `static/*` 必须**重建镜像**（COPY 进镜像，非挂载）并 bump `sw.js`

### 5.4 部署 / 运维
- [ ] `docker-compose` 里的凭据来自 `.env`，不入库
- [ ] 新增系统依赖写进 `Dockerfile`，并**实测 recreate 后仍可用**
- [ ] 危险操作脚本（`purge-all.sh` 一类）有二次确认 + 干跑模式
- [ ] 文档与代码同步更新（改了行为就改 README）

### 5.5 文档
- [ ] 结论先行，能被单独读懂
- [ ] 数字来自实测，不写"大约/应该是"
- [ ] 未完成项与已知限制**如实列出**，不美化

## 六、反模式库（本项目真实案例）

> 每条都附**真实位置**与**修复方式**，供审查时直接对照。

| # | 反模式 | 真实案例 | 修复 |
|---|---|---|---|
| A1 | **位置契约** | `wv_media.py::_conv_hash_map` 固定 `r[3]`，`run_link` 传 3 列 → 静默返回空 | 统一列序为 `(msg_id, source_file, ts)` 并全调用方对齐 |
| A2 | **缓存被绕过** | `run_wxam` 直调 `_plain_sizes()` 而未走 `_PSIZES_CACHE`，明文库被扫两遍 | 改为 `_PSIZES_CACHE.get(k) or _plain_sizes(k)` |

| A4 | **变量未初始化即使用** | `run_files` 引用了从未赋值的 `_OUT_DIR["out"]` | 显式把 `out` 作为参数传入 |
| A5 | **静默吞异常** | `wv_raw.py:100`、`wv_media.py:183`、`wv_archiver.py:462` 等 29 处 | 加日志或注明可忽略的理由 |
| A6 | **语义错配的 UI** | 会话行用"未读"绿胶囊展示**总条数**，且与上一行文本重复 | 计数改为弱化数字；第二行改为真正有用的信息（时间跨度） |
| A7 | **非幂等的中间产物** | 早期解码并发写同一 `.tmp` 名 → 第二个进程 `rename` 失败 | 唯一临时名（带 pid）+ `os.replace` |
| A8 | **未声明的隐式依赖** | `ffmpeg`/`pilk`/`gcc` 只存在于容器可写层，`recreate` 即丢 | 写进 Dockerfile 或固化钩子 |
| A9 | **工具链约束未记录** | 在 NAS 上 `sh -c` 单引号嵌套必被吞、Git Bash 把 heredoc 里 `\n` 变 `/n` —— 各踩坑多次 | 写入团队约定：一律「脚本 base64 注入文件再执行」 |
| A10 | **死代码累积** | `resolve_conv_hash` 被替换后仍保留 30+ 行 | 删除；确需保留则标注 `# deprecated: 由 _conv_hash_map 取代` |

## 附录 B · Definition of Done

一个变更算"完成"，当且仅当：

1. `preflight.sh` 🔴 = 0
2. 按 §4.1 完成对应级别的审查，意见全部回应（修了或明确记账）
3. 高风险变更完成 §4.3 三件事
4. 文档/README 与行为同步
5. PR 模板填写完整，**已知限制如实写明**
6. 涉及的产物已归档（截图进 `_shots_*/`，报告进 `docs/`）

> —— 标准的意义不在于"写下来的那天"，而在于**下一次有人想省事时，它挡得住**。
