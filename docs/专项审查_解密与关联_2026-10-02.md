## 二、F1 · `run_link` 必然崩溃（最严重）

**位置**：`archiver/wv_media.py:397` 与 `:410`

```python
chash = _conv_hash_map(conn, rows, plain_dbs)
c2h = None                       # ← L397：永远是 None
...
for r in rows:
    ...
    uk = hashlib.md5(k.encode()).hexdigest()
    if uk in c2h.get(r["ts"], ()):   # ← L410：None.get() → AttributeError
        h_pool.add(uk)
```

**根因**：这是我在「统一列序」重构时引入的。原本是
`chash, c2h = resolve_conv_hash(rows, psizes)` 一次性返回两个结构，
后来拆成 `_conv_hash_map` 只返回 `chash`，`c2h` 被随手写成 `None` 占位，
但**下游 `c2h.get()` 的调用没删也没改**。

**为什么危险**：这不是"偶发崩溃"，是**确定性崩溃**——只要跑 `link` 命令就必崩。
而它崩在循环里、在已经 `print("会话↔哈希 映射…")` 之后，
粗看日志会以为"跑到关联了"，实际还没开始回填就死了。

**修复**：恢复真实的二次校正逻辑——`c2h` 应是「真实 username 的 md5 集合」，
用于判断某条消息的显示名是否恰好也是一个合法 username（此时直接 md5 命中磁盘目录）。
新增 `_ct_hash_map()` 从 contact 表取 username 全集，调用点改为成员判断 `uk in c2h`。

**验证**：真机重跑 `link`，不再崩，回填 72,970 条（98.5%），
且 `convs_matched` 359 → 366（二次校正额外救回 7 个会话）。

## 三、F2 · 缺少固定块自检（密钥错误的硬信号被浪费）

**位置**：`wv_media.py:74` 定义了 `FIXED_BLOCK` 常量，但**从未使用**；
`decode_dat`（L219-233）与 `wv_wxam.v2_strip` 都没有校验它。

**背景**：V2 `.dat` 布局中，`[15+aes_size : 15+aes_size+16]` 这 16 字节
**对任何账号、任何文件都恒等于** `4b34278883a017cadb25201c644dafad`（已实测 100/100 验证）。

**为什么危险**：`decode_dat` 目前的正确性只依赖两个弱条件——
① `aes_size % 16 == 0` ② 总长度自洽。这两个都不涉及**密钥是否正确**。
如果 aes_key 错了（比如 wxid 候选选错），AES 会解出均匀随机字节，
最后靠 `plain.startswith(magic)` 的 magic 匹配"侥幸"返回 None。
但这个 magic 匹配是**弱校验**：`RIFF`、`BM` 这类 2 字节 magic，
随机字节有 1/65536 概率撞上，量大时必然出现假阳性。

**修复**：解密前先校验固定块 `blob[15+aes_size:15+aes_size+16] == FIXED_BLOCK`，
不匹配直接返回 None。这 16 字节是**零成本的强校验**——把"密钥错误"从
"靠 magic 碰运气"变成"确定性拒绝"。

**验证**：真实 .dat 抽样 100 个，固定块 **100/100 匹配**，确认不会误杀正常文件。

## 五、审查方法（本次沉淀，供复用）

这次审查没有"猜"，而是**把完整代码读进来逐行推演**，因此能发现 F1 这种
"静态看是 None，运行才崩"的确定性 bug。三个关键动作：

1. **读全量，不读摘要**——F1 藏在 L397/L410 两行，中间隔了 13 行，只读函数签名会漏
2. **追踪变量的完整生命周期**——`c2h` 从赋值到使用跨了 13 行 + 一个 for 循环，
   必须确认每次使用时的真实类型
3. **真机验证，不靠静态断言**——语法通过 ≠ 能跑；固定块常量"看起来对" ≠ 真的对，
   用 100 个真实样本验证后才敢说"不会误杀"

## 六、遗留待办（如实列出）

- **建议**：给 `decode_dat` / `run_link` 补单元测试——这两处正是"错了不报错"的类型，
