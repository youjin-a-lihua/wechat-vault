## 🔴 B1 · 尺寸映射被覆盖，导致图片关联丢数据

**位置**：`archiver/wv_media.py:392`、`archiver/wv_media.py:1109`

```python
# _plain_sizes()
if sizes:
    out[(h, ct)] = sizes          # ← 同一 (会话, 时间戳) 后写的覆盖先写的

# _plain_thumb_len()
if v and v.isdigit() and int(v) > 0:
    out[(h, ct)] = int(v)          # ← 同样会覆盖
```

**为什么是 Bug**：`create_time` 只精确到**秒**。同一会话同一秒发多张图（批量发图、转发多图）时，这多条消息映射到同一个 key，**只有最后一条的尺寸被保留**，其余消息关联不上。

**实测证据**（真实库）：

```
图片消息总行数:              77883
唯一 (会话,时间戳) 键:        74103
冲突键（同秒同会话多条图片）:   2054     ← 每个冲突键丢掉 N-1 条
受影响消息行数:              约 3780 条（4.9%）
例: hash=eaa66cb4 ts=1790392641 共 4 条 → 只保留 1 条
```

**影响**：直接压低「消息↔图片」关联命中率。当前 98.5% 的命中率里，这 4.9% 里有一部分本可命中。

**建议修复**：

```python
# _plain_sizes
out.setdefault((h, ct), []).extend(sizes)

# _plain_thumb_len —— 同一秒多图时保留所有尺寸
out.setdefault((h, ct), []).append(int(v))
```

> ⚠️ 注意：`_plain_thumb_len` 的消费方（`run_wxam` 里 `tl.get((h, ts))` 当作标量用）需要同步改为遍历列表，否则会因类型变化报错。**改这两处必须一起改消费方**。

## 🔴 P1 · `/api/stats` 全库统计：冷态 7.93 秒

**位置**：`viewer/wv_server.py:api_stats`

**问题**：一次请求里跑了 **6 条互不相关的全表扫描**，每条都要遍历 133 万行。

**实测分解**（冷 page cache）：

| 查询 | 耗时 |
|---|---|
| ① `COUNT(*)` | 0.025s |
| ② `MIN(ts) / MAX(ts) / SUM(CASE WHEN is_self=1...)` | **6.066s** ← 主要瓶颈 |
| ③ `GROUP BY type` | 0.373s |
| ④ `GROUP BY sender` | 0.598s |
| ⑤ `GROUP BY account` | 0.245s |
| ⑥ 按小时 `GROUP BY strftime(...)` | 0.620s |
| **合计** | **7.926s** |

**补充实测**（热 page cache）：同一条 ② 只要 **0.160s**。
→ 说明**冷态慢主要是磁盘 I/O**，但「6 条独立扫描读同一批数据」仍在热态下多花约 1.8s。

**建议修复**（两条腿）：

1. **合并聚合**：把 ①② 合成一条
   ```sql
   SELECT COUNT(*), MIN(ts), MAX(ts), SUM(is_self) FROM msg [WHERE ...]
   ```
   实测热态 **0.205s**（含全部四项），替换原来的 ①② 两条。

2. **结果缓存**：统计结果只在归档（`/api/ingest`、`/api/reload`）后失效
   ```python
   _STATS_CACHE: dict[tuple, tuple[float, dict]] = {}
   # key = (conv_id, account)；命中且未过期 → 直接返回
   ```
   归档是每天 03:00 一次，缓存命中率接近 100%。

**预期收益**：冷态首次 ≈ 7.9s → 合并后约 7s（I/O 主导，收益有限）；**热态 2s → 0.2s**；**加缓存后重复访问 ≈ 0ms**。

## 🔴 P2 · 明文库被完整扫描两遍

**位置**：`archiver/wv_media.py:355` `_plain_sizes()` 与 `:1077` `_plain_thumb_len()`

**问题**：两个函数逻辑 **95% 相同**（同样的 glob、同样的 `WHERE local_type=3`、同样的 zstd 解压、同样的正则），只是提取的字段不同：

| | `_plain_sizes` | `_plain_thumb_len` |
|---|---|---|
| 提取字段 | `length` / `hdlength` / `cdnthumblength` | 只有 `cdnthumblength` |
| 缓存 | 有 `_PSIZES_CACHE` | **无** |
| 实测耗时 | **7.53s** | **1.01s** |

**调用关系**：`run_link` 调 `_plain_sizes`，`run_wxam` 调 `_plain_thumb_len`。
跑 `wv_media.py all` 时**同一批 817 个表被解压 + 正则两遍**。

**建议修复**：合并成一个函数，一次扫描同时产出两样：

```python
def _plain_media_meta(plain_dbs: str) -> tuple[dict, dict]:
    """一次扫描，返回 (sizes_map, thumb_len_map)。"""
    sizes: dict[tuple, list[int]] = {}
    thumb: dict[tuple, list[int]] = {}
    ...  # 单次 glob + 单次解压 + 单次正则
    return sizes, thumb
```

并给它加缓存，`run_link` / `run_wxam` 共用。

**预期收益**：省掉一整轮 817 表扫描（实测约 1s CPU + 一次磁盘遍历），且 `_plain_thumb_len` 从「无缓存」变为「有缓存」。

## 🔴 P3 · 会话列表排序让索引失效

**位置**：`viewer/wv_server.py:665`、`:1102`

```sql
SELECT * FROM conv ORDER BY COALESCE(end_ts,0) DESC LIMIT 500
```

**问题**：`COALESCE(end_ts,0)` 是表达式，SQLite **无法使用 `end_ts` 上的索引**，必须全表扫描 + 临时排序。

**实测**：**0.894s**（`conv` 表仅数百行，本该是亚毫秒级）。

**建议修复**：SQLite 里 `NULL` 在 `DESC` 排序中默认排在**最后**，与 `COALESCE(end_ts,0)` 的语义在「`end_ts` 为 NULL 视为最旧」这件事上等价：

```sql
ORDER BY end_ts DESC          -- 走索引
```

若确需把 NULL 当 0 参与比较，可建**表达式索引**：
```sql
CREATE INDEX IF NOT EXISTS idx_conv_end_ts ON conv(COALESCE(end_ts,0) DESC);
```

## 🔴 P4 · 全库导出把全部正文拼成一个字符串

**位置**：`viewer/wv_server.py:export_all`

**问题**：`_fetch_convs()` 取全部会话 → 逐会话生成 HTML/TXT → **`"".join(chunks)` 拼成单个超大字符串**。

**实测量级**：
```
消息 1,333,012 条，正文合计 24.7 MB
→ 加 HTML 标签/样式后，最终字符串约 100 MB+
→ 生成过程中峰值内存可达 200–400 MB（原串 + 中间串 + 编码后的 bytes）
```

**影响**：不会 OOM（NAS 内存够），但导出时**会明显卡顿**，且多用户同时导出会叠加。

**建议修复**：改用 `StreamingResponse` 逐会话 yield，不累积大字符串：

```python
def gen():
    yield HEADER
    for c in convs:
        yield X.conv_to_html(c).decode("utf-8")
    yield FOOTER
return StreamingResponse(gen(), media_type="text/html; charset=utf-8")
```

## 💭 微优化

**N1. `SUM(CASE WHEN is_self=1 THEN 1 ELSE 0 END)` 可简化为 `SUM(is_self)`**
实测 0.160s → 0.148s（约 7%）。可读性略降，收益小，可选。

**N2. `decode_dat` 未对 `aes_size == 0` 做显式拒绝**
`aes_size=0` 时 `AES.decrypt(b"")` 返回空，若尾部恰好以图片 magic 开头会返回「成功」。实际几乎不可能出现，且后续长度检查已拦住超大值。**判定为无需修改**，仅记录。

## 修复过程中新发现的问题

### 🔴 P5 · 定时归档从未真正运行（README 与实现不符）

`deploy/entrypoint.sh` 里有完整的 `scheduler.sh`（每天 03:00 归档），但：

```
容器 ENTRY = [/init]          ← s6-overlay，不是 entrypoint.sh
镜像内不存在 /entrypoint.sh   ← 该文件是运行时的孤儿文件，无人调用
/app/scheduler.sh 不存在      ← 从未生成
/data/logs/scan.log 不存在    ← 从未执行过
```

**结论：README 写的「每天 03:00 自动归档」在当前部署里不成立**，所有归档都必须手动触发。

**修复**：把调度器（含媒体链路）挂到真正生效的 `/config/.config/openbox/autostart`，
并同步 `/defaults/autostart`（防 `01-wv-autostart` 钩子覆盖）。

### 🟡 P6 · `docker cp` 后文件权限变成 0000（部署陷阱）

用 `docker cp` 覆盖容器内 `.py` 后，文件权限变为 `----------`（0000），
而服务以 `abc`(uid 1000) 运行 → `Permission denied` → 看守循环每 2 秒重启一次，
表现为「容器 healthy 但页面打不开」。

**修复**：部署脚本必须显式 `chmod 644`。

**已写进教训**：任何 `docker cp` 部署后必须校验 `md5` + `chmod` + 用服务账号试读。

### 🟡 P7 · `autostart` 的 `set -u` 与子 shell 变量

往 `autostart` 加代码时，若在主 shell 引用只在 `( ... ) &` 子 shell 内定义的变量，
`set -u` 会让整个脚本**静默退出**，导致后续「拉起微信」等逻辑全部不执行。
（本次修复中实际踩到：表现为微信不再自动启动。）

**修复**：日志里不引用子 shell 变量。

> 只做 AST 静态检查很容易漏掉：`call_next`（函数参数）、`MEMORY_BASIC_INFORMATION`（class）都是误报，
> 必须结合上下文判断。

## 实现的方案

### 1. 手动按钮（已有入口，补齐能力）

前端「归档」面板里本来就有按钮，改为：
- 文案：`立即归档` → **`立即解析（含图片）`**
- 提示：`放进目录后点下方按钮；5 分钟内也会自动解析（只处理新增文件）`
- 后端 `/api/ingest` 追加 **③ 媒体链路**（`wv_media.py all` + `extras`）

⚠ 关键细节：媒体脚本依赖 `pycryptodome` + `zstandard`，**只有 `wx-venv` 有**；
viewer 跑在 `wv-venv` 上，因此必须用另一个解释器（`WV_MEDIA_PYTHON`，默认 `/opt/wx-venv/bin/python3`）。

实测：`POST /api/ingest` → `ok=true readable=true raw=true media=true`，耗时 **250s**（首次全量）。

### 2. 自动解析（从「每天一次」改为「有新文件就解析」）

调度器改为双触发：

```
A) 每 WV_AUTO_SCAN_MIN 分钟（默认 5）用 find -newer 检查 inbox
   → 有新文件就 do_archive()（文字 + 存档轨 + 媒体链路 + reload）
B) 每天 WV_SCAN_HOUR（默认 3）点做一次全量 + 冷备
```

- 关掉即时解析：`WV_AUTO_SCAN_MIN=0`
- 关掉每日：`WV_SCAN_HOUR=off`
- 关掉媒体链路：`WV_MEDIA_AUTO=0`

### 3. 路径修复

`ln -sfn /data/inbox_v4 /data/inbox`（数据卷内软链接，持久化）

### 🔴 P12 · `find` 不跟随符号链接 → 自动解析仍然不生效

上一轮建的软链接 `/data/inbox -> /data/inbox_v4`，调度器用：

```sh
NEWF=$(find "$INBOX" -type f -newer "$STAMP" …)   # ← 返回 0
```

**GNU find 默认不跟随命令行参数里的符号链接**，所以永远返回 0 个文件，
「检测到新文件就解析」形同虚设。

实测对照（stamp 设为 2020-01-01）：

```
不加 -L: 0
加 -L  : 469     ← 唯一差异
```

同时确认 **Python 侧不受影响**（`os.walk('/data/inbox')` = 469 个文件），
所以 `wv_archiver scan`、`/api/ingest` 一直是正常的，只有 shell 的 find 有问题。

**修复**：`find -L "$INBOX" …`

> 教训：凡是「软链接 + shell 工具」的组合都要实测。`os.walk` 跟随、`find` 不跟随——
> 两套语义不同，不能互相推断。
